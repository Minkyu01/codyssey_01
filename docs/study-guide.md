# 개발 워크스테이션 학습 가이드

이 가이드는 `purpose.md`의 여섯 학습 목표를 현재 프로젝트에 연결합니다. 각 절의 “평가 답변”을 자신의 말로 설명하고, 확인 명령까지 실행할 수 있으면 학습 목표를 충족한 것입니다.

## 전체 흐름

```text
Dockerfile + nginx/default.conf + site/
                  │ docker build
                  ▼
        workstation-web:1.0 이미지
                  │ docker run
                  ▼
            컨테이너:80
            ├── -p 8080:80 ── 호스트 브라우저·curl
            ├── bind mount ── 호스트 파일 즉시 반영
            └── named volume ─ 컨테이너 삭제 뒤에도 데이터 유지

작업 디렉터리 ── git commit ── 로컬 Git 저장소 ── git push ── GitHub 원격 저장소
```

## 1. 절대 경로와 상대 경로

절대 경로는 파일 시스템의 시작점부터 위치를 적습니다. macOS와 Linux에서는 `/`로 시작합니다. 상대 경로는 현재 작업 디렉터리를 기준으로 계산합니다.

현재 프로젝트 루트에서 두 경로는 같은 파일을 가리킵니다.

```text
절대 경로: /path/to/ex01/nginx/default.conf
상대 경로: nginx/default.conf
```

```bash
pwd
ls -l nginx/default.conf
```

Docker 빌드의 `COPY nginx/default.conf ...`도 빌드 컨텍스트 `.`을 기준으로 상대 경로를 해석합니다. 다른 디렉터리에서 빌드하거나 컨텍스트를 바꾸면 같은 문자열이 다른 파일을 가리킬 수 있습니다.

자주 하는 오해는 상대 경로가 “짧은 절대 경로”라는 생각입니다. 상대 경로의 의미는 `pwd`가 바뀌면 함께 바뀝니다.

평가 답변:

> 절대 경로는 루트부터 위치가 고정됩니다. 상대 경로는 현재 디렉터리를 기준으로 계산됩니다. 이 프로젝트의 Dockerfile은 빌드 컨텍스트 `.`에서 `nginx/default.conf`와 `site/`를 찾습니다.

## 2. 파일 권한과 숫자 표기

권한 문자열은 파일 종류와 세 사용자 범주의 권한을 나타냅니다.

```text
- rw- r-- r--
│  │   │   └─ 기타 사용자
│  │   └───── 그룹
│  └───────── 소유자
└──────────── 파일 종류(-: 일반 파일, d: 디렉터리)
```

`r`, `w`, `x`의 숫자값은 각각 `4`, `2`, `1`입니다. 각 범주의 값을 더해 세 자리 숫자로 적습니다.

| 표기 | 계산 | 의미 |
|---|---|---|
| `644` | `6=4+2`, `4`, `4` | 소유자는 읽기·쓰기, 나머지는 읽기 |
| `755` | `7=4+2+1`, `5=4+1`, `5=4+1` | 소유자는 모든 권한, 나머지는 읽기·실행 |

현재 프로젝트의 일반 파일은 `644`, `nginx/`와 `site/` 디렉터리는 `755`로 확인할 수 있습니다.

```bash
stat -f '%Sp %N' Dockerfile nginx site site/index.html
```

Linux에서는 다음 명령을 사용합니다.

```bash
stat -c '%A %n' Dockerfile nginx site site/index.html
```

파일의 `x`는 실행을 뜻합니다. 디렉터리의 `x`는 내부 항목에 접근하고 경로를 통과할 수 있다는 뜻입니다.

평가 답변:

> 권한은 소유자·그룹·기타 사용자 순서로 읽습니다. `644`는 `rw-r--r--`, `755`는 `rwxr-xr-x`입니다. 디렉터리의 실행 권한은 프로그램 실행이 아니라 내부 경로 접근 권한입니다.

## 3. Dockerfile과 커스텀 이미지

`Dockerfile`은 이미지를 만드는 명령 목록입니다. 이미지는 실행에 필요한 파일과 설정을 담은 읽기 전용 템플릿입니다. 컨테이너는 그 이미지를 실행한 인스턴스입니다.

[Dockerfile](../Dockerfile)은 `nginx:1.27.5-alpine`을 기반으로 다음 항목을 추가합니다.

- [nginx/default.conf](../nginx/default.conf)를 NGINX 설정 경로에 복사
- [site/](../site/index.html)를 문서 루트에 복사
- 데이터 디렉터리 생성과 `nginx` 사용자 소유권 설정
- 컨테이너 포트 `80` 선언
- `/healthz` HTTP 상태 검사

```bash
docker build -t workstation-web:1.0 .
docker image inspect workstation-web:1.0
```

`EXPOSE 80`은 이미지가 사용하는 포트를 문서화합니다. 호스트에 포트를 공개하지는 않습니다. 실제 공개는 `docker run -p`가 담당합니다.

고정된 버전 태그는 `latest`보다 재현성이 높습니다. 다만 태그 대신 이미지 digest까지 고정해야 완전히 같은 바이트를 보장할 수 있습니다.

평가 답변:

> Dockerfile은 설계도, 이미지는 빌드 결과, 컨테이너는 이미지의 실행 인스턴스입니다. 이 프로젝트는 NGINX 설정·정적 사이트·헬스체크를 추가해 커스텀 이미지를 만듭니다.

## 4. 포트 매핑

컨테이너는 호스트와 분리된 네트워크 공간을 사용합니다. 컨테이너 안에서 NGINX가 `80` 포트를 열어도 호스트 브라우저가 자동으로 접근할 수는 없습니다.

```bash
docker run -d \
  --name workstation-web \
  -p 127.0.0.1:8080:80 \
  workstation-web:1.0
```

매핑을 왼쪽부터 읽으면 다음과 같습니다.

```text
127.0.0.1 : 8080  →  container : 80
호스트 주소   호스트 포트          컨테이너 포트
```

`127.0.0.1`에 바인딩하면 같은 컴퓨터에서만 접근할 수 있습니다. `0.0.0.0:8080:80`은 호스트의 모든 네트워크 인터페이스에 게시하므로 방화벽과 네트워크 환경에 따라 외부에서 접근할 수 있습니다.

```bash
docker ps --filter name=workstation-web
curl -fsS http://127.0.0.1:8080/healthz
```

평가 답변:

> 컨테이너는 별도 네트워크 공간을 사용하므로 호스트 포트와 컨테이너 포트를 연결해야 합니다. `127.0.0.1:8080:80`은 로컬 호스트의 8080 요청을 컨테이너의 80으로 전달합니다.

## 5. Docker 볼륨과 영속 데이터

컨테이너의 쓰기 레이어는 컨테이너를 삭제하면 함께 사라집니다. Docker 볼륨은 컨테이너와 생명주기를 분리해 데이터를 유지합니다.

[compose.yaml](../compose.yaml)은 다음 경로에 이름 있는 볼륨을 연결합니다.

```text
workstation-data → /usr/share/nginx/html/data
```

| 저장 방식 | 지정 대상 | 적합한 용도 | 컨테이너 삭제 뒤 데이터 |
|---|---|---|---|
| 컨테이너 쓰기 레이어 | 별도 지정 없음 | 임시 실행 상태 | 사라짐 |
| 바인드 마운트 | 호스트 경로 | 소스·설정의 즉시 반영 | 호스트 파일로 유지 |
| 이름 있는 볼륨 | Docker 볼륨 이름 | DB·업로드·영속 데이터 | 볼륨을 지우기 전까지 유지 |

볼륨 검증은 반드시 다음 순서를 포함해야 합니다.

1. 첫 컨테이너가 볼륨에 파일을 씁니다.
2. 파일 내용을 확인합니다.
3. 첫 컨테이너를 삭제합니다.
4. 새 컨테이너에 같은 볼륨을 연결합니다.
5. 같은 파일을 다시 읽습니다.

단순히 `docker volume ls`를 실행하는 것만으로는 영속성을 증명할 수 없습니다. 전체 실습은 [재구성 가이드](./getting-started.md)에서 확인할 수 있습니다.

평가 답변:

> 볼륨은 Docker가 관리하는 별도 저장 공간입니다. 첫 컨테이너를 삭제하고 새 컨테이너가 같은 볼륨의 파일을 읽어야 영속성이 증명됩니다.

## 6. Git과 GitHub

Git은 로컬 버전 관리 도구입니다. 커밋, 브랜치, 변경 이력을 인터넷 연결 없이 관리할 수 있습니다. GitHub는 Git 저장소를 원격에서 호스팅하고 협업 기능을 제공합니다.

| 항목 | Git | GitHub |
|---|---|---|
| 실행 위치 | 로컬 컴퓨터 | 원격 서비스 |
| 핵심 역할 | 변경 추적, 커밋, 브랜치 | 저장소 공유, Pull Request, 리뷰 |
| 대표 명령·동작 | `git add`, `git commit`, `git log` | `git push`, 웹 저장소, 이슈 |
| 인터넷 필요 여부 | 로컬 작업은 불필요 | 원격 통신에 필요 |

현재 저장소의 로컬 상태와 원격 주소는 다음 명령으로 확인합니다.

```bash
git status --short
git branch --show-current
git remote -v
git log --oneline -5
```

`git remote -v`에 GitHub 주소가 있다고 해서 최신 커밋이 원격에 올라갔다는 뜻은 아닙니다. `git status`, 로컬·원격 브랜치 비교, 실제 GitHub 파일 트리를 함께 확인해야 합니다. VS Code의 GitHub 로그인은 계정 상태이므로 사용자가 직접 화면을 확인하고 민감정보를 가린 증거를 준비해야 합니다.

평가 답변:

> Git은 내 컴퓨터에서 변경 이력을 관리합니다. GitHub는 Git 저장소를 원격에 보관하고 협업하게 합니다. 원격 주소 설정만으로 푸시 완료나 VS Code 로그인까지 증명되지는 않습니다.

## 셀프 체크

- 현재 디렉터리가 바뀌면 상대 경로가 어떻게 달라지는지 설명할 수 있습니다.
- `640`, `644`, `750`, `755`를 권한 문자열로 바꿀 수 있습니다.
- Dockerfile·이미지·컨테이너의 차이를 설명할 수 있습니다.
- `8080:80`의 왼쪽과 오른쪽을 구분할 수 있습니다.
- 바인드 마운트와 볼륨의 용도를 비교할 수 있습니다.
- Git 원격 설정과 GitHub 푸시 완료를 별개의 증거로 판단할 수 있습니다.

평가 준비 순서는 [평가 학습 계획](./evaluation-study-plan.md), 실제 시연 흐름은 [동료 평가 가이드](./peer-review.md)를 참고합니다.
